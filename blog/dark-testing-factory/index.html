The Dark Testing Factory: lights out, quality on

Black Friday is coming, the promotions team just changed the deal rules, and the code freeze is on Friday. I built UiPath's "dark testing factory" for a fictional retailer's checkout to see how much of it is real today: AI-written test cases, robots in the cloud, a schedule that runs while everyone sleeps, and an agent that tests the shop with no script at all. Mistakes included.

Jarryd Scott Technical Lead, Business Automation · host of UiPath Uncharted
Hands-on deep dive

Lights out, quality on

In manufacturing, a dark factory is a plant so automated it can run with the lights off. Robots build, inspect and move product through the night, and people show up to decide what gets built next. UiPath borrowed the idea for software testing and called it the dark testing factory: a quality system where test generation, execution, analysis and maintenance run around the clock inside the delivery pipeline.

It sounds like a slide. So I did what this blog always does and built it. Not on a client, not on a sandbox demo someone else prepared, but on my own dev tenant, against a real (small) web shop, with every command, error and screenshot left in.

  • Lights on

    Testing today

    Three testers, a spreadsheet of test cases, a regression pack that takes two days by hand, and a release that waits for all of it.

  • Lights out

    The factory

    AI writes the tests from the requirements, robots run them on every change and every night, failures become defects on their own, and agents go looking for the bugs nobody wrote a test for.

  • The catch

    Humans still decide

    UiPath is clear that the factory is about removing people from repetitive testing work, not from quality. Somebody still decides what "ready to ship" means.

Before you read on: a challenge

The shop in this post is live at uipathuncharted.co.za/shop. It has two deliberate bugs that cost money. Give yourself five minutes to find them before the robots spoil it for you. The answers are in section 6.

The use case: Black Friday Eve at Kudu & Co

Meet Kudu & Co, a made-up online retailer. Think biltong, rooibos, coffee, air fryers and a kettle braai, all on special. Two weeks before Black Friday the promotions team drops the final deal rules: 3 for 2 on Pantry items, 20% off with a promo code, free delivery over R750, double loyalty points and a limit of 5 per product. The code freeze is in five days. The test team is three people.

If you have ever worked retail in South Africa (or anywhere, really), you know how this ends: somebody tests the happy path, somebody else tests the code on one product, and on the night a customer discovers that two deals stack and the shop gives away margin until Monday.

About the shop

Kudu & Co is fictional. The shop is one HTML page I built for this post, with no backend, and nothing is for sale. Everything else is real: the Test Manager project, the AI output, the Playwright runs on UiPath's cloud robots, the defects and the autonomous agent all ran on my dev tenant, and every screenshot is from there. I planted two bugs in the pricing code, the kind that slip through a busy release: one that costs money on every order, and one that is only off by a cent.

The promotions brief became seven requirements. They are short on purpose, the way real ones are:

  • BF-01 3 for 2 on Pantry
  • BF-02 BLACKFRIDAY code
  • BF-03 Delivery
  • BF-04 VAT
  • BF-05 Rewards points
  • BF-06 Limit of 5
  • BF-07 Place an order

From lights on to lights out

UiPath describes the factory as a maturity path, not a product you buy. Here is that path as I would explain it to a client, with an honest label on each step: what you can use today, what is in preview, and what is still a vision. Click through.

People click through test scripts

Test cases live in a tool or a spreadsheet and a tester runs each one by hand. Thorough when there is time, skipped when there is not. Most teams still have a lot of this.

  • Available today
  • Test Manager manual runs

Robots run the scripts

Studio test automation or, new this year, your own Playwright suite, packaged and run by Test Manager on cloud robots. A person still writes every test and decides when to run it.

  • Available today
  • Used in this post

AI writes and reviews the tests

Test Manager reads a requirement and proposes test cases, critiques the requirement itself, and flags test cases that no longer match. A person reviews what it produces.

  • Available today
  • Used in this post

Agents test on their own

You give an agent a mission and a URL and it explores the application, invents its own scenarios and reports findings with screenshots and repro steps. UiPath has also announced Autopilot running a manual test case with no automation behind it.

  • Preview
  • Autonomous Exploration used in this post

Governed autonomy

Agents generate, run, triage and repair tests continuously inside the pipeline, under policy. People set the rules: acceptable risk, who signs off and what "done" means for a release. UiPath's words: testers "move from running tests to governing the system that runs them".

  • Building blocks exist

The rest of this post climbs that path one step at a time on the Kudu & Co checkout: scripts first, then AI, then an agent, and an honest look at how close step five really is.

Hands-on: building the factory

I drove all of this from Claude Code with the UiPath skills loaded, mostly the uipath-test skill, which teaches the agent to use uip tm, the Test Manager part of the UiPath CLI. Every command below is one that ran, and every output is real (trimmed for length). The screens at the end are Test Manager in the browser.

You need The UiPath CLI (uip) A coding agent with the UiPath skills Test Manager on your tenant Node.js for Playwright
  1. 01

    Check the tenant, then create a project

    ~5 min

    Confirm you are in the right tenant before you create anything, then create a Test Manager project and give it a default Orchestrator folder. Runs resolve packages and robots through that folder.

    Terminal
    $ uip login status --output json
    $ uip tm project create --name "Kudu & Co Black Friday" --project-key KUDU --output json
    "ProjectKey": "KUDU", "Name": "Kudu & Co Black Friday"
    $ uip tm project set-default-folder --project-key KUDU --folder-key <folder-key> --output json
    "Result": "Updated"
  2. 02

    Load the requirements

    ~15 min

    Each Black Friday rule becomes a requirement with rules and acceptance examples. This is the most important step in the whole factory: every AI feature downstream reads these descriptions, so vague requirements give you vague tests.

    Terminal
    $ uip tm requirements create --project-key KUDU --name "BF-02 BLACKFRIDAY promo code" --description "$(cat bf-02.md)" --external-reference PROMO-102 --output json
    "Key": "KUDU:2"
    # ...and six more, KUDU:1 to KUDU:7
  3. 03

    Let the AI write test cases

    ~1 min each

    One command starts a background AI job that reads the requirement and proposes test cases with steps and expected results. Each start uses AI units, so start it once and reuse the job id to review and create. I ran it on the three money rules: 3 for 2, the promo code and VAT.

    Terminal
    $ uip tm requirements generate-testcases --project-key KUDU --requirement-key KUDU:2 --wait --timeout 540 --output json
    [wait] AI activity ca7f178a... reached terminal status: Processed (took 00:00:30)
    #1 Validate promo code BLACKFRIDAY applies 20% discount to non-discounted item
    #5 Validate promo code applies only to non-discounted items in mixed basket
    #10 Validate promo code with leading and trailing spaces is rejected
    # 10 proposals. I kept six. More on #10 below.
    $ uip tm requirements generate-testcases --project-key KUDU --activity-id ca7f178a... --create --select 1 2 4 5 6 9 --output json
    "Result": "Success" (6 created, labelled autopilot-generated)
    Review, don't rubber-stamp

    Across three requirements the AI proposed 30 test cases in about 30 seconds each. I kept 17. Section 5 explains the 13 I rejected, because that is where the human earns their place.

  4. 04

    Let the AI critique a requirement

    ~1 min

    The same AI can review a requirement before anyone builds against it. I pointed it at the delivery rule. It came back with twelve suggestions, and some were sharp.

    Terminal
    $ uip tm requirements evaluate --project-key KUDU --requirement-key KUDU:3 --wait --timeout 540 --output json
    * The R99.00 delivery fee doesn't say whether it includes VAT. In South Africa, VAT typically applies to delivery fees.
    * Define whether R749.99, R750.00 and R750.01 each qualify for free delivery.
    * The requirement mentions '3 for 2 deal' but provides no details about how this promotion works.
    # ...12 in total
    Read between the lines

    The VAT-on-delivery question is a genuinely good catch: my requirement never said. The third one shows a limit: the 3 for 2 rules are fully defined in BF-01, but the AI reads each requirement on its own, so it cannot see them.

  5. 05

    Automate with Playwright

    ~1 hour

    The AI test cases describe what to check; something still has to click. I wrote a 17-test Playwright suite, one describe block per requirement, using the shop's data-testid attributes. Here is the test that matters most:

    tests/black-friday.spec.ts 
    test.describe('BF-02 BLACKFRIDAY promo code', () => {
  test('mixed basket: code applies to the speaker only', { tag: ['@pricing', '@money'] }, async ({ page }) => {
    await add(page, 'BILTONG-250', 2);
    await add(page, 'ROOIBOS-80');
    await add(page, 'SPEAKER-BT');
    await applyCode(page, 'BLACKFRIDAY');
    // 20% of the speaker only. The biltong and rooibos are already on 3 for 2.
    await expect(page.getByTestId('code-discount')).toHaveText('-R259.80');
  });
});

    My first local run had five failures. Three were the planted bugs. The other two were my bug: the shop shows a zero saving as R0.00 and my test expected -R0.00. Tests have bugs too, and a red test is a question, not a verdict.

    Terminal
    $ npx playwright test
    Expected: "-R0.00" Received: "R0.00"
    5 failed, 12 passed (56.7s)
    # fix the test, not the shop
    $ npx playwright test
    3 failed, 14 passed (41.9s)
  6. 06

    Pack it for Test Manager

    ~5 min

    This is the part that was "coming soon" in UiPath's September announcement and simply worked on my tenant in October. uip tm pack turns a normal Playwright project into a package. Upload it to Orchestrator and Test Manager creates one test case per Playwright test, with labels for the file, suite, tags and browser.

    Terminal
    $ uip tm pack --project-path pw --type playwright --project-key KUDU --name KuduBlackFridayTests --package-version 1.0.0 -o out --output json
    "Package": "KuduBlackFridayTests@1.0.0", "TestCount": 17
    $ uip or packages upload out/KuduBlackFridayTests.1.0.0.nupkg --output json
    "Status": "OK"
    # about 20 seconds later: 17 test cases, labelled PW_File_*, PW_Suite_*, PW_Tag_money ...
  7. 07

    Build a test set that maintains itself

    ~5 min

    A test set assigned by dynamic label picks up every test in the spec file, including ones added next week, without anyone editing the set. Then link each automated test to its requirement so coverage means something.

    Terminal
    $ uip tm testsets create --project-key KUDU --name "Black Friday Regression" --output json
    "TestSetKey": "KUDU:42"
    $ uip tm testcases add --test-set-key KUDU:42 --labels "PW_File_tests/black-friday.spec.ts" --dynamic --output json
    "MatchedTestCases": 17, "Result": "Added"
    $ uip tm requirements testcases --project-key KUDU --requirement-id <id> --add-testcase-ids <ids> --output json
  8. 08

    Run it on cloud robots

    ~1 min

    No laptop, no VM, no robot to keep logged in. The test set runs on UiPath's serverless cloud robots against the live shop. The folder needs a serverless machine and a robot account that can run unattended; mine already had both.

    Terminal
    $ uip tm testsets run --test-set-key KUDU:42 --playwright-project chromium --output json
    "ExecutionId": "1ef670d4...", "Status": "Pending"
    $ uip tm wait --execution-id 1ef670d4... --project-key KUDU --timeout 120 --output json
    "Status": "Finished", "Duration": "00:00:36"
    $ uip tm executions get-stats --execution-id 1ef670d4... --project-key KUDU --output json
    "Passed": 14, "Failed": 3
  9. 09

    Turn failures into defects

    ~2 min

    A defect is raised from one failed result and carries the test, the run and the evidence. With Jira or Azure DevOps connected it syncs across; without one it lives in Test Manager. I made the two stacking bugs High (they lose money on every order) and the VAT bug Medium.

    Terminal
    $ uip tm executions testcaselogs list --execution-id 1ef670d4... --project-key KUDU --only-failed --output json
    $ uip tm defects create --project-key KUDU --execution-id 1ef670d4... --test-case-id <id> --output json
    "Name": "BF-02 BLACKFRIDAY promo code > code does not stack on 3 for 2 items - Failed"
    $ uip tm defects update --project-key KUDU --defect-id <id> --priority High --output json
  10. 10

    Switch the lights off: a nightly schedule

    ~2 min

    This is the "dark" part in its simplest form: the regression runs at 02:00 every night whether anyone remembers or not. Watch the cron: Test Manager uses Quartz, which starts with seconds, not Unix cron. I created mine switched off, with an end date, because a demo should never keep running on a tenant after the blog post is done.

    Terminal
    $ uip tm schedules create --test-set-key KUDU:42 --name "Lights out - nightly Black Friday regression" --cron "0 0 2 1/1 * ? *" --cron-details '{"type":4,"daily":{"atHour":2,"atMinute":0,"frequencyIndays":1}}' --recurrence recurrence --timezone Africa/Johannesburg --start-time 2026-11-11T18:00 --disable-time 2026-11-18T23:59 --disabled --output json
    "IsEnabled": false, "Action": "Created"
  11. 11

    Try a load test (and hit a wall)

    ~5 min

    Black Friday is a load problem as much as a logic problem, and Test Manager has performance scenarios. I set one up for 200 virtual shoppers on the checkout test. The dry run refused the package.

    Terminal
    $ uip tm perf-scenario execute --scenario-key KUDU:43 --wait --output json
    "Message": "HTTP 400: Failed to restore or download package KuduBlackFridayTests. Project metadata file not found in package."
    Honest result

    Performance scenarios want a Studio-built test package, not a Playwright one, and a full run needs performance testing licence units (my dev tenant has none). Load testing is part of the factory, just not for this suite on this tenant. I left it as a known gap rather than fake it.

What the AI got right, and wrong

Generating test cases is the headline feature, so it deserves a proper review. Thirty proposals, seventeen kept. Here is what the other thirteen taught me.

Four lessons · click a row

  • Every example I wrote in a requirement came back as a test case with the exact numbers, including the mixed basket that catches the stacking bug. Write good examples and you get good tests almost for free.

  • One proposal insisted a code typed with spaces around it must be rejected. The requirement never says that, and most shops would trim the spaces. A test like that fails for the wrong reason and somebody wastes an afternoon "fixing" correct code.

  • Boundary thinking is good, but the cheapest product is R64.99 and you can buy at most five of anything, so neither basket can exist. It also proposed a test for an item "priced at R99.99" that is not in the catalogue. The AI knows the requirement, not the product.

  • Three test cases for case sensitivity, nine for 3 for 2 quantities. Cheap to generate, not cheap to maintain. I kept one of each pattern. Generated tests still cost money every time they run and every time the UI changes.

The takeaway

AI test generation turns a tester from a writer into an editor. That is a big speed-up, and it moves the skill to two places: writing requirements with sharp examples, and saying no to plausible-looking tests that check the wrong thing.

Red, amber, green

Here are the answers to the challenge. The first cloud run found exactly the two planted bugs, through three failing tests:

  • Bug 1 · High

    The deals stack

    BLACKFRIDAY is meant to skip items already on 3 for 2. It does not. On 2 biltong, 1 rooibos and a speaker the shop gives R335.80 off instead of R259.80. Three rooibos get R26.00 off when they should get nothing. Every Black Friday basket with Pantry items leaks margin.

  • Bug 2 · Medium

    VAT is out by a cent

    VAT is rounded on every line and then added up, instead of once on the total. On a R618.98 order the shop shows R80.73; the right answer is R80.74. No customer will notice. Finance will, at month end, across thousands of orders.

Then I fixed the shop one bug at a time, pushed each fix live and re-ran the same test set on the cloud robots. Three runs, one afternoon:

The part I did not expect: open a failed result and Test Manager shows Playwright's own error report, which is written for an AI to read. It literally starts with instructions: explain why the test failed, be concise, provide a fix. Hand it to your coding agent and you have the start of automated triage.

Letting the agent loose

Everything so far is scripted. A person wrote every check. The step that makes the factory "dark" is different: an agent that tests what nobody wrote a test for. In Test Manager it is called Autonomous Exploration, it is in preview, and it lives on the requirement page. Before running it I put both bugs back in the shop, so it had something real to find.

My mission was simple: explore like a deal-hunting customer, check the maths on every line, report anything that looks wrong. Eleven minutes later:

Three things happened, and all three matter:

  • Found

    The expensive bug

    It found the stacking bug with no test written for it, and noticed something my tests did not: Pantry items get the 20% even when the 3 for 2 has not kicked in yet.

  • False alarm

    "Double points" is not doubled

    It reported a Medium bug: the banner says double points, so it expected 4 per R10, not 2. The shop is correct, but the banner never says what normal is. Not a bug, but a fair point about the copy.

  • Ran out of time

    VAT never got checked

    Only 1 of the 10 scenarios completed. Serverless exploration is capped at 10 minutes, and the VAT scenario was cut off. The cent bug went unreported.

Scripts guard, agents explore

Put the two side by side. The scripted suite caught both bugs every run in 36 seconds, but only because someone knew to check them. The agent found the expensive bug with no script, but missed the subtle one and raised a false alarm. That is not a weakness of either: the factory needs both, and a person to triage what the agent says.

Where the lights stay on

After a day in the factory, this is where I still needed a human, and where I think you will too.

  • Input

    Requirements are the product

    Every AI feature reads the requirement text. Good examples gave me good tests; a missing rule (VAT on delivery) went untested until the AI asked. Garbage in is now automated garbage out.

  • Judgement

    Triage

    Five red tests on day one: three real bugs, two broken tests. One agent finding was a false alarm. Somebody has to decide which is which before a developer loses a day.

  • Limits

    Timeboxes and licences

    Exploration stops at 10 minutes on serverless. Load testing needs Studio packages and licence units. AI generation spends AI units on every start. Plan for these like any other capacity.

  • Risk

    What "ready" means

    Is a one-cent VAT bug a release blocker on Black Friday Eve? A robot cannot answer that. Someone who owns the risk can.

  • Hygiene

    Clean up after demos

    Schedules, preview credits and test data outlive the experiment. My schedule was created switched off with an end date for exactly that reason.

  • Maintenance

    Someone owns the suite

    Seventeen tests is easy. Seventeen hundred generated ones is a codebase. UiPath's vision has agents repairing tests too; until then, somebody does.

The next few years

UiPath calls the full dark testing factory a longer-term vision, with some building blocks available today. Having built what exists, here is how I read the road ahead. This part is opinion, and I have labelled it that way.

My read · click a row

  • Everything in the hands-on section works today: AI test generation and requirement review, your own Playwright suite in Test Manager, serverless cloud robots, defects and schedules. A team could run its Black Friday regression lights-out tonight. Most of the effort is writing the requirements well.

  • Autonomous Exploration is usable in preview and already finds real bugs. UiPath has announced Autopilot running manual test cases with no automation, and self-healing for Playwright selectors. My bet: within a year or so, the normal setup is scripted regression on every change plus an agent exploring every night, with a person triaging the agent's findings in the morning.

  • The full factory: agents notice a change, decide what to test, run it, triage the failures, repair broken tests and route real defects, inside the pipeline, under policy. People set acceptable risk and sign off. The building blocks are visible; joining them up safely, with audit trails a regulator would accept, is the real work. I would want to see that running at a bank before I called it done.

Why now

UiPath's argument is that AI coding tools let teams ship code much faster than they can test it, and that testing has to scale the same way. After watching my own coding agent write a shop and a test suite in an afternoon, I find that hard to argue with. If code is cheap, checking it has to get cheap too.

Test yourself

Q1Which planted bug did the autonomous agent miss?

It found the expensive stacking bug, but the 10-minute serverless timebox cut off its VAT scenario. The scripted test caught it on every run.

Q2On the first local run, five tests failed. How many were real bugs in the shop?

Three failing tests, covering the two planted bugs. The other two failures were my test expecting "-R0.00" where the shop correctly shows "R0.00".

Q3How do you add next week's new Playwright tests to the Black Friday test set?

The set was filled with --dynamic on the spec file's PW_File label, so anything ingested from that file joins automatically. And never use link-automation on Playwright cases: ingestion links them.

Pick an answer for each one.

Your turn: beat the robots

Both bugs are back in the Kudu & Co shop, exactly as the robots found them. Now that you know what they are, here are three things to try:

  • Easy

    Reproduce the stack

    Two biltong, one rooibos, one speaker, code BLACKFRIDAY. Work out what the promo saving should be before you look.

  • Harder

    Find the missing cent

    One biltong and one coffee. Is the VAT really 15/115 of the total? Find another basket where it is wrong.

  • Bonus

    Out-test the agent

    Point your own Playwright suite or agent at the shop. Find something none of us reported and tell me on LinkedIn.
